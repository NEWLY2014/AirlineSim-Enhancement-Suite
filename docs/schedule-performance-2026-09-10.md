# 大型航司 Schedule 保存响应性修复

日期：2026-09-10。修复前基线：`4e52e669671dbacf4d177892e1a1a7fe672c59a6`。

## 问题与改动

原实现点击提取后同步遍历全部航班行，每行多次执行 jQuery 查询。随后在内容脚本中读取航司所有历史 schedule、合并当天快照并重新写入；历史对象的解码和序列化占用游戏页面主线程。

当前实现每处理 100 行或消耗约 8 毫秒就让出事件循环，以原生 DOM 查询提取字段，显示提取行数及准备/保存状态。历史读取、合并和写入转移到扩展后台；页面只发送当天快照。后台按航司串行保存，保留原键名、完整历史、未知元数据及备份格式。

后台写入前向请求文档再次确认页面所有权。提取过程中如果表格发生变更则中止并允许重试，避免异步分批期间混入不同时点的数据。重复启动、空数据、存储失败及自动提取导航仍受到保护。

## Chromium 本地验证

本地 HTTPS 游戏页面夹具包含 10,000 条航班行，Chrome 真实存储预置 30 天同等规模历史。使用隔离 Chromium 加载扩展，没有访问真实游戏或执行实际业务操作。

| 指标 | 基线 | 修复后 |
| --- | ---: | ---: |
| 页面 5 ms 定时器观察到的最长间隔 | 938.2 ms | 35.7 ms |
| 点击处理连续占用时间 | 58.9 ms | 0.7 ms |
| 提取期间绘制的不同进度状态 | 0 | 45 |
| 从点击到完成检测的总耗时（含约 100 ms 观测尾窗） | 1.88 s | 5.87 s |

本次改善的是页面响应性，**并未缩短该用例的总保存时间**。分批让出执行和后台历史处理会增加总耗时；已有历史仍按兼容格式整条重写，后台 I/O 和序列化成本仍随历史规模增长。上述为本机单次观测，不是线上 SLA；浏览器、设备负载、航线分布和历史规模均影响结果。定时器间隔用于观测页面响应，不等同于某一函数的精确 CPU 时间。

新增浏览器用例要求提取期间实际绘制多个不同进度状态，且最终 31 天数据与所有 10,000 条新航班完整保留。使用基线构建运行同一用例，因缺少中间进度绘制而失败；当前构建通过。
